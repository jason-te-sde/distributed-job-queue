# Comparison with River and Asynq

This page compares the queue with two Go job queues that a reader is likely to weigh it against: [River](https://github.com/riverqueue/river), which keeps its jobs in PostgreSQL, and [Asynq](https://github.com/hibiken/asynq), which keeps them in Redis. Everything said about River or Asynq comes from their own README, documentation site, wiki or Go API reference, read on 2026-11-18, and each cell names its source in the list under the table. Where those sources did not settle a question, the cell says "not checked" rather than guess. What is said about this queue comes from this repository: the [README](../README.md), [docs/architecture.md](architecture.md) and the [design records](design/0001-postgres-as-source-of-truth.md).

## What each one is

**This queue** is a service. Producers and workers are programs of their own that use the Go SDK and talk gRPC to a set of stateless brokers. They never connect to the database; the brokers do, and in PostgreSQL 15 to 18 every job is a row of one table. The Helm chart in `deploy/helm/jobqueue` runs the brokers as a Deployment of two replicas by default. Any broker can serve any call, and KEDA scales the workers on the backlog. Putting a broker between the clients and the database is a choice with costs, a network hop and a service to run, and [ADR 0001](design/0001-postgres-as-source-of-truth.md) gives the reasons, River's library model among the alternatives it rejected.

**River** is a library. A River client runs inside the application, inserts jobs and works them over the application's own database, and River encourages using the same database for application data and the queue [R1]. PostgreSQL is its primary target, and SQLite support is described as experimental [R2] [R17]. There is no service of its own to deploy: the maintenance work (pruning finished jobs, rescuing stuck ones, inserting periodic jobs) runs in whichever client wins a leader election held in the database [R12] [R16], and River UI is a separate web application that reads the same database [R14]. Besides Go, River ships implementations in Java, JavaScript/TypeScript, Ruby and Rust, which share one schema, and Python can insert jobs [R1] [R2] [R15]. The version current when the sources were read was v0.51.2 [R8].

**Asynq** is a library backed by Redis 4.0 or newer [A1]. A `Client` in the producing program puts tasks on queues in Redis, and a `Server` in the worker program pulls them and runs a goroutine for each [A1]. Redis holds the queues and the tasks [A1] [A5]; Asynq can follow a Redis Sentinel failover [A9], and its README warns that some of its Lua scripts may not work with Redis Cluster [A1]. A web UI (Asynqmon) and a CLI inspect and control queues and tasks [A1]. The version current when the sources were read was v0.26.0, and the README says the API may still change before v1.0.0 [A1] [A2].

## Semantics

| | This queue | River | Asynq |
| --- | --- | --- | --- |
| Delivery guarantee | At-least-once. With a downstream sink that keeps the highest fencing token it has seen for a job, or an idempotent one, each effect happens once ([README](../README.md#what-it-is)) | At-least-once: a job can run again after a worker error, a crash, or a completion that failed to save. A worker that completes its job with `JobCompleteTx` in its own transaction gets the guarantee that a committed attempt never runs again [R3] | At-least-once execution, and automatic recovery of the tasks of a crashed worker [A1] |
| How a job is claimed | A lease, handed out by a broker in answer to a long poll. Rows are picked with `FOR UPDATE SKIP LOCKED`; the lease lasts 30 s by default on the database clock and is renewed by heartbeats every quarter of that. A reaper on every broker takes expired leases back once a second, each as a failed attempt ([architecture](architecture.md#leases-heartbeats-and-acknowledgements)) | A client's fetch locks a batch of available jobs [R5] and works them under a job timeout, 1 minute by default [R3]. The pages read describe no heartbeat. A job still running after `RescueStuckJobsAfter` (1 hour by default, or the job timeout plus an hour when that timeout is longer) is rescued by the leader: made ready to run again, or discarded if its attempts are used up [R4] | The worker server holds a lease on each active task and extends it with heartbeats. A task whose lease was not extended is orphaned, fails with `ErrLeaseExpired`, and is recovered by a server that runs its queue [A2]. The length of the lease: not checked |
| What stops a stalled worker from overwriting a newer owner's result | Fencing tokens. `lease_epoch` grows by one on every lease, and Heartbeat, Complete, Fail and Release apply only under the current one, so a stalled worker's late report is refused as `FENCED`. `Job.Token()` lets a downstream system refuse the stalled worker's writes as well ([ADR 0002](design/0002-leases-and-fencing.md)) | The docs say that a rescued job may run again alongside the attempt that was still running [R4]. Whether a late completion or write from that earlier attempt is refused: not checked | Not checked |
| Retries and backoff | Up to `max_attempts`, 25 by default (1 to 100). The delay doubles from 1 s to a cap of 1 h, with full jitter. A handler can choose the delay (`RetryAfter`) or send the job straight to `dead` (`Permanent`), and `jobqueuectl requeue` brings a dead job back | 25 attempts by default, the first run included. The delay is the attempt count to the fourth power in seconds, plus or minus 10% (1 s, 16 s, 1 min 21 s, ...), which puts the last retry about three weeks after the first run; a job whose attempts are used up is discarded. The policy can be changed per client and per worker [R3] [R6] | Up to 25 retries by default, with exponential backoff; `RetryDelayFunc` replaces the policy. A task that exhausts its retries moves to the archive for inspection. `SkipRetry` archives it at once, and `IsFailure` can mark an error that does not use up a retry [A3] |
| Scheduling across tenants or queues | Within a queue, weighted deficit round robin over the tenants that have ready work: a tenant's turn is 8 jobs times its weight (1 to 1000), so one tenant's flood does not starve the others. Each broker plans alone, so fairness across brokers is approximate. No priorities; `--scheduler fifo` gives arrival order ([ADR 0005](design/0005-drr-fair-scheduling.md), [ADR 0007](design/0007-scope.md)) | Several queues, each with its own number of workers on each client [R7]. Within a queue, priorities 1 to 4, applied strictly: higher-priority jobs are always fetched first, and lower-priority ones may not be fetched while higher ones keep the workers busy [R8]. Concurrency limits per tenant, by partitioning on a job argument, are a River Pro feature [R9]. Weighted sharing between tenants: not checked | Weighted priority between the queues of a server: with weights 6, 3 and 1, the queues are served 60%, 30% and 10% of the time while none is empty. With `StrictPriority`, a queue is served only when every higher one is empty [A2] [A4]. A tenant dimension apart from queues: not checked |
| Transactional enqueue with the application's own writes | No. An enqueue is a gRPC call to a broker, outside the application's database transaction. An idempotency key, the caller's or one the SDK generates for each call, makes a repeated call safe | Yes, and it is the design's centre: `InsertTx` inserts the job in the application's transaction, so the job exists if that transaction commits, is removed if it rolls back, and is not visible to workers before the commit [R1] [R10]. Completion can join the worker's transaction too (`JobCompleteTx`) [R3] | Not checked. The tasks live in Redis [A1], a store apart from an application's SQL database |
| Unique jobs | An idempotency key names one job within its tenant and queue for as long as the row exists, which is until 24 hours after the job succeeded or was cancelled and 14 days after it became dead. A repeated key returns the first job, marked as deduplicated | Unique by any combination of arguments, kind, period, queue and state; a duplicate insert is skipped [R11] | Two ways. `TaskID`: at any moment one task has a given ID, and a second enqueue fails with `ErrTaskIDConflict`. `Unique(ttl)`: a lock on the task's type, payload and queue, released when the task succeeds or the TTL ends, which the docs call best effort [A2] [A5] |
| Periodic jobs | Not offered: cron is out of scope. Put a scheduler in front of the queue, or have a handler enqueue the next run ([ADR 0007](design/0007-scope.md)) | Fixed intervals or cron schedules, inserted by the leader, which keeps the schedule in memory, so it starts over after a restart or a new election. Durable periodic jobs, whose run times are kept in the database, are a River Pro feature [R12] | A `Scheduler` enqueues tasks on a schedule. Only one scheduler may run for a schedule, or the tasks are duplicated; `PeriodicTaskManager` adds and removes schedules at run time [A6] |
| Cancellation | `Cancel`, from the SDK or `jobqueuectl cancel`, makes a ready or leased job `cancelled`. A leased job's holder is fenced from then on and learns at its next heartbeat, when the SDK cancels the handler's context | `JobCancel` by job ID, whether the job is waiting or running. A waiting job is cancelled at once; a running one is marked and its worker's context is cancelled, and a worker that still returns success completes the job. A worker can also cancel its own job [R13] | `Inspector.CancelProcessing`, or `asynq task cancel`, sends a cancellation signal to an active task, on a best-effort basis. `DeleteTask` removes a task that is pending, scheduled, waiting for a retry or archived. A `Timeout` or `Deadline` on a task ends its handler's context [A2] [A7] |
| Observability | Prometheus metrics (enqueues, leases, acknowledgements by result including `fenced`, reaps, jobs per queue and state, store latency), structured JSON logs, and `jobqueuectl` for jobs, queue statistics and the dead list. No web UI and no tracing ([docs/operations.md](operations.md), [ADR 0007](design/0007-scope.md)) | Subscriptions to job and queue events, metrics hooks that include the duration of the fetch query, an OpenTelemetry plugin for Go, and River UI [R5] [R14] | Prometheus queue metrics through the web UI or a separate exporter, worker metrics by instrumenting the handlers, and a CLI with a dashboard [A1] [A8] |
| Client languages | Go: the SDK and `jobqueuectl`. The gRPC protocol in `proto/jobqueue/v1` is public and versioned, so a client in another language can be generated from it; none ships ([ADR 0007](design/0007-scope.md)) | Go, Java, JavaScript/TypeScript, Ruby and Rust, which can insert and work jobs and interoperate: a job inserted in one can be worked in another. Python can insert jobs. Each connects to the database through a driver of its language [R1] [R2] [R15] | Go [A1]. Clients in other languages: not checked |

## Performance

The one measurement is E6 of [docs/benchmarks.md](benchmarks.md#e6-river-as-a-reference). River v0.50.0 ran as a library inside the benchmark process, inserting and working jobs over the database with no network hop, on the laptop of the other experiments (an Apple M2 with 8 cores and 16 GB of memory) against the same local PostgreSQL 17, with 256 workers, 20 database connections, a `FetchCooldown` of 1 ms (River's default is 100 ms), 64-byte payloads and 30-second probes. Its highest sustained rate was 10,250 jobs per second at the median of three runs (10,250 to 11,469), 2.7 times the 3,781 of one broker (2,844 to 4,250). The difference includes the network hop from the producer and from the worker to the broker, the fenced lease that every job here gets, and fair scheduling across tenants, and the experiment did not separate them: it is a reference point, not a comparison of like with like. It ran on the code of commit `8f72a3c`, and was not repeated on later commits or on later versions of River.

Asynq was not measured.

## When to use which

- **River**, when the producer is an application on the same PostgreSQL and wants each job enqueued in its own transaction, committed with its writes or not at all. It runs in the application's process with no service to deploy, ships in five languages that share one schema, has priorities, unique jobs, periodic jobs and a web UI, and on the one laptop measured here it moved 2.7 times the jobs of one broker. Every process that inserts or works jobs connects to the database, and the pages read do not say what stops a rescued job's earlier attempt from finishing it.
- **Asynq**, when Redis is already there, the code is Go, and the work can live in a store apart from the application's database, with the gap between the two writes that River's docs describe [R10]. Its README and wiki do not state how durable an enqueued task is. It has weighted and strict queue priorities, periodic tasks, unique tasks and a web UI.
- **This queue**, when producers or workers should not connect to the database (they run on another network, should hold no database credentials, or are written in a language that River does not ship) and a versioned gRPC API is wanted instead; when tenants share a queue and must be isolated by weight rather than ordered by priority; or when a stalled worker must be fenced, by the queue and, through `Job.Token()`, by the system it writes to. The price is a service to run, a network hop, no transactional enqueue, no priorities, no periodic jobs and no web UI, and only the Go client ships.
